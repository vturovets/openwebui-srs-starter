# CR-004 SRS – Free-Text Preference → Filter Mapping

for **NLP-Powered Holiday Request Prototype**

Version: 0.1  
Date: 2025-12-09

---

## 1. Context and Purpose

The existing **NLP-Powered Holiday Request** prototype accepts natural-language requests and converts them into structured holiday search parameters (`from`, `to`, `departureDate`, `durationId`, party, rooms), via a deterministic pipeline and pluggable methods (rules, LLM, hybrid). The system is already wired to OpenWebUI, supports bulk imports, and exposes performance and accuracy summaries for different parsing methods.

The **new business requirement**:

> “The system must allow users to enter additional free-text information (e.g. keywords) together with the standard search criteria and use it to refine the search, by mapping the free-text to existing filter(s)/filter option(s) and applying these filters so that the returned results satisfy both the standard search criteria and the interpreted free-text input.”

This SRS defines the scope and requirements to add a **“preference mapping” capability**:

- Interpret free-text **preferences** (e.g. *“I need internet access in all my rooms”*, *“I don’t need catering but scuba diving facilities must be available”*).

- Map that text to **existing filters and options** defined in `filters_options.csv`.

- Apply the mapped filters to refine the holiday search results.

- Reuse the existing pipeline, UI frame, logging, and import/summary capabilities to **benchmark multiple methods** (rules, LLM, hybrid, etc) for this new task.

The capability is **mutually exclusive** with the existing “free-text holiday search” mode: at any point the user either issues a search request or adds preferences, but not both in the same query.

---

## 2. Business Value

From the client story and existing project vision:

1. **Higher search relevance & conversion**
   
   - Users can phrase details in plain language (*“no all-inclusive, I just need room only and scuba”*) and get the right filters automatically (e.g. `Boards = Room Only`, `Facilities = Scuba`). This reduces friction and mis-configured searches.

2. **Better UX for non-expert users**
   
   - Users do not need to know the full filter taxonomy–they can just describe needs, and the system maps them to structured options in `filters_options.csv`.

3. **Faster experimentation on NLP methods**
   
   - The prototype is explicitly used for A/B/C testing of different approaches. The new preference mapping task adds another **benchmark surface** (accuracy of mapping vs. ground truth, P95 latency) using the same import and statistical summary machinery (CR-003).

4. **Reuse of existing infrastructure**
   
   - Reuses FastAPI backend, CSV logging, import runner, and `/v1/import/summary` statistics service (P95, accuracy bootstrap/binomial tests).

5. **Foundation for richer personalization**
   
   - Once free-text preferences are reliably mapped to filters, the same approach can later power:
     
     - Profile-based defaults (e.g. *always* Wi-Fi, no catering).
     
     - Preference summaries and “assumed filters” explanations.
     
     - More complex reasoning (multi-preference trade-offs) using the same LLM infrastructure and popularity Imputer ideas.

## 4. Scope and Assumptions

### 4.1 In Scope

- A new **interpretation mode** for the main text/voice input:
  
  - **Mode A – “Holiday Request”**: existing behaviour (parse holiday search request into `from`, `to`, `departureDate`, etc.).
  
  - **Mode B – “Preference Mapping”**: interpret same text field as **preferences** that map to filters/options.

- **Mapping free-text to filters/options** such as:
  
  - *“I need internet access in all my rooms”* → `Facilities: Free Wi-Fi`, `Facilities: Wi-Fi*`, `Holiday Type: Holiday by WXYZ – Free Wi-Fi`.
  
  - *“I don’t need catering but scuba diving facilities must be available”* → `Boards: Room Only`, `Facilities: Scuba`, `Facilities: Scuba - additional info`.

- Reading the list of **filters and options from `filters_options.csv`** (canonical catalogue).

- Reusing the **left control console** with changes:
  
  - Console title change.
  
  - Removal of specific inputs.
  
  - Renaming the primary input label to “Add your preferences”.
  
  - Keeping `Method`, `Parse request`, `Import CSV`, `Export CSV`, `Reset`.

- Ability to **evaluate methods** for preference mapping using:
  
  - Import operations.
  
  - `/v1/import/summary` statistical processing: P95, accuracy, thresholds, confidence intervals.

### 4.2 Out of Scope (for this CR)

- Changing the core holiday search validation rules or pipeline stages for `from`, `to`, `departureDate`, etc. (only **augmenting** search with filters).

- New destination/airport/duration fixture semantics.

- Multi-turn preference refinement dialogs beyond what the existing dialog orchestrator already supports (if enabled).

- Major visual redesign; changes are limited to wording and presence/absence of controls.

- Integration with the existing search request capabilities.

### 4.3 Key Assumptions

- `filters_options.csv` is the **single source of truth** for filters and options and can be extended if necessary.

- Ground-truth mappings can be prepared in CSV form to compute accuracy via the existing import/summary mechanism.

- The same methods catalog (`methods.yaml`) and `Method` dropdown are used to configure preference mapping strategies.

- This document covers the general requirements to introduce the capability. The detailed method descriptions on how to process user inputs and map them to particular options are provided in separate implementation guides.

## 5. High-Level Process Descriptions

### 5.1 Existing Holiday Request Flow (Mode A) – Reference

Already defined in SRS/SDD and kept unchanged: user enters a holiday request, pipeline parses, normalises and validates parameters, logs to CSV.

**Simplified steps:**

1. Open web app.

2. Enter holiday request (text or voice).

3. Backend `/v1/parse` pipeline:
   
   - detect language → extract → normalise → validate → log.

4. UI displays structured request and validation status.

### 5.2 New “Preference Mapping” Flow (Mode B – Direct entry)

1. **User selects mode:**
   
   - In the left console, user chooses **“Preferences”** (e.g. via a toggle or mode selector; see UI section).

2. **User enters free-text preferences:**
   
   - Example: *“No catering, but scuba diving facilities must be available and Wi-Fi in all rooms.”*

3. **User selects method (optional):**
   
   - Chooses a method from `Method` dropdown (e.g. `rules`, `llm`, `hybrid`) – same catalogue as existing pipeline (however, the methods differ).

4. **User triggers parsing:**
   
   - Clicks `Parse request`.

5. **Backend preference-mapping pipeline:**
   
   - Receives `{ text, mode=preferences, method }`.
   
   - Loads `filters_options.csv` and preference-mapping configuration.
   
   - Extracts **intent and constraints** from text.
   
   - Maps them to filters and filter options:
     
     - Positive preferences (must-have).
     
     - Negative preferences (pick the relevant options, e.g. "Room only").
   
   - Builds a structured **FilterSelection** result.

6. **UI displays mapped filters/options:**
   
   - Grouped by filter (e.g. *Facilities*, *Boards*).
   
   - Shows which parts of text triggered which filters (optional highlight).

7. **Logging & telemetry:**
   
   - The mapping call is logged in CSV (method, processing time, filters/options selected).
   
   - If invoked via an import job, its performance and accuracy feed into `/v1/import/summary`.

### 5.3 Import / Evaluation Flow for Preference Mapping

Reuses existing import runner and summary endpoint.

1. Analyst prepares a CSV with:
   
   - `text` – free-text preference.
   
   - Expected filters/options (ground truth).

2. Import runner posts each `text` to the backend in **preference mode**.

3. Backend logs output + metadata to CSV.

4. Frontend invokes `/v1/import/summary`, which:
   
   - Filters timing outliers (`P95_OUTLIERS_THRESHOLD`).
   
   - Computes P95 latency vs threshold `IMPORT_P95_THRESHOLD_MS` via bootstrap.
   
   - Computes **accuracy** vs `IMPORT_ACCURACY_THRESHOLD` via binomial test (exact).

5. Summary is shown in **Performance summary** and **Usage footprint summary** sections, consistent with CR-003 UI.

## 7. Functional Requirements

### 7.1 Interpretation Mode and UI Console Changes

1. **Mode switch**
   
   - FR-01 – The UI SHALL provide a clear control to select between:
     
     - `Holiday request` mode (existing behaviour).
     
     - `Preferences` mode (new mapping behaviour).
   
   - FR-02 – Only one mode SHALL be active at any given time.

2. **Left control console updates** (Preferences mode)
   
   - FR-03 – The console title SHALL be updated to reflect preference mapping (exact wording TBD with UX).
   
   - FR-04 – The following fields SHALL be **hidden/removed** in Preferences mode:
     
     - `Default Participants`
     
     - `Flexibility, days`
     
     - `Airports`
     
     - `Destinations`
   
   - FR-05 – The `Method` dropdown SHALL remain available and continue to list the available parsing methods loaded from the backend `/v1/fixtures` response.
   
   - FR-06 – The main input label text `Ask for a holiday` SHALL be changed to `Add your preferences` in Preferences mode.
   
   - FR-07 – Buttons `Parse request`, `Import CSV`, `Export CSV`, and `Reset` SHALL remain visible and functional in Preferences mode.

3. **Voice input**
   
   - FR-08 – Voice input behaviour SHALL remain unchanged; in Preferences mode voice transcripts SHALL be treated as free-text preferences instead of holiday requests.

### 7.2 Backend API and Mode Handling

4. **Mode parameter**
   
   - FR-09 – The backend SHALL support a mode indicator in the request (e.g. `interpretation: "search" | "preferences"`),  via a dedicated endpoint `/v1/preferences/parse`. Concrete path is to be specified in SDD.
   
   - FR-10 – When `interpretation="search"`, the existing pipeline (language detect → extract → normalise → validate) SHALL remain unchanged.
   
   - FR-11 – When `interpretation="preferences"`, the backend SHALL:
     
     - Skip core holiday search validation and instead run **preference mapping**.
     
     - Still perform language detection and logging as in the main pipeline.

5. **Response structure (Preferences mode)**
   
   - FR-12 – The response in Preferences mode SHALL include at least:
     
     - `filters`: an array of `{ filterId, filterLabel, options: [{ optionId, optionLabel, selected: bool, confidence: number }] }`.
     
     - `metadata.method` and `metadata.mode` (including the selected method alias and `interpretation="preferences"`).
     
     - `metadata.timings.totalMs` and `thresholdBreached` as in the existing pipeline.
   
   - FR-13 – Optionally, `metadata.mappings` MAY expose text spans or tokens that triggered each filter option for observability.

### 7.3 Filters and Options Catalogue

6. **filters_options.csv ingestion**
   
   - FR-14 – The backend SHALL load `filters_options.csv` from a configurable path (e.g. under `FIXTURES_DIR`).
   
   - FR-15 – On startup, the system SHALL validate that `filters_options.csv`:
     
     - Exists and is readable.
     
     - Uses a consistent delimiter (configured or default).
   
   - FR-16 – The internal representation of filters and options SHALL be cached and reused across requests for performance.

7. **Minimum supported semantics**
   
   - FR-17 – For each filter, the system SHALL track:
     
     - A unique filter identifier.
     
     - A human-readable label (e.g. “Facilities”, “Boards”).
   
   - FR-18 – For each filter option, the system SHALL track:
     
     - A unique option identifier.
     
     - A label (e.g. “Free Wi-Fi”, “Room Only”, “Scuba – additional info”).
   
   - FR-19 – The design SHALL allow extension of the CSV with synonyms / keyword hints if required by specific methods (details in SDD).

### 7.4 Preference-Mapping Logic

8. **Core mapping rules**
   
   - FR-20 – Given free-text preferences, the system SHALL detect semantics like:
     
     - Required facilities (Wi-Fi, scuba, pool, etc.).
     
     - Board preferences (room only, half-board, all-inclusive).
     
     - Optional vs. negative preferences (e.g. *“no catering”*).
   
   - FR-21 – The mapping SHALL be constrained to filters and options present in `filters_options.csv`; it SHALL NOT introduce options outside the catalogue.

9. **Method selection and extensibility**
   
   - FR-22 – For Preference mode, the backend SHALL support multiple methods (rules, LLM, hybrid, etc) configured in the methods catalogue, similar to the holiday request pipeline.
   
   - FR-23 – The design SHALL allow reusing components and services already implemented for summaries/inferences where appropriate. 

10. **Handling ambiguity / low confidence**
    
    - FR-24 – If the system cannot confidently map any option, it SHALL:
    
    - Return an empty `filters` array or all `selected=false`.
    
    - Include an explanatory status in metadata (e.g. `status: "no-preferences-detected"`).

### 7.5 Logging and Import / Summary Integration

11. **Transaction logging**
    
    - FR-26 – Each preference-mapping request SHALL be logged in the CSV with the existing schema plus any necessary extension to capture mapped filters/options (e.g. as JSON in the `Output` column).
    
    - FR-27 – `Status` SHALL indicate success/failure of the mapping process.

12. **Import summary integration**
    
    - FR-28 – Preference-mapping import runs SHALL submit raw run data to `/v1/import/summary` (or reuse the same endpoint) including:
    
    - Response times for each row.
    
    - A boolean accuracy outcome per row (correct mapping vs. ground truth) for the active method.
    
    - FR-29 – The summary service SHALL apply:
    
    - P95 bootstrap inference vs `IMPORT_P95_THRESHOLD_MS`.
    
    - Accuracy binomial test vs `IMPORT_ACCURACY_THRESHOLD`.
    
    - Minimum sample size `MIN_SAMPLE_SIZE` and `P95_OUTLIERS_THRESHOLD` logic as described in CR-003.

13. **UI summary blocks**
    
    - FR-30 – In Preferences mode, the `Performance summary` and `Usage footprint summary` sections SHALL show:
    
    - P95, P95 threshold, P95 inference text and confidence level.
    
    - Accuracy, accuracy threshold, accuracy inference text and confidence level.
    
    - “Insufficient data” messages when `MIN_SAMPLE_SIZE` not met.

### 7.6 Error Handling

14. **Configuration errors**
    
    - FR-31 – If `filters_options.csv` is missing or invalid, the backend SHALL:
    
    - Log an error.
    
    - Return a clear error response for preference-mapping calls.
    
    - Allow holiday request mode to continue functioning normally.

15. **Runtime errors**
    
    - FR-32 – Any unexpected exception in preference mapping SHALL:
    
    - Be recorded in logs.
    
    - Return a failure response with `Status = failed` in CSV.

## 8. Non-Functional Requirements

These extend the existing NFRs for the prototype.

1. **Performance**
   
   - NFR-01 – Preference-mapping requests SHALL respect the global processing threshold `PROCESSING_THRESHOLD_MS` (default 1000 ms). A flag in metadata SHALL indicate when the threshold is breached.
   
   - NFR-02 – Import summary calculations for preference mapping SHALL adhere to P95 and accuracy threshold rules defined in CR-003 (`IMPORT_P95_THRESHOLD_MS`, `IMPORT_ACCURACY_THRESHOLD`, `P95_OUTLIERS_THRESHOLD`, `MIN_SAMPLE_SIZE`, `ALPHA`).

2. **Usability**
   
   - NFR-03 – UI changes (mode switch, label change, removal of controls) SHALL remain minimal and intuitive; no additional login/auth flows.
   
   - NFR-04 – The visual design SHALL remain consistent with existing OpenWebUI-based layout.

3. **Maintainability**
   
   - NFR-05 – Preference-mapping logic SHALL be implemented as a **separate service/module** in the backend (e.g. `PreferenceMapperService`), so that it can be replaced or extended without touching existing holiday search pipeline components.

4. **Scalability & Extensibility**
   
   - NFR-06 – The solution SHALL support multiple mapping methods without schema changes (only configuration changes and method catalogue updates).

5. **Localization**
   
   - NFR-07 – For MVP, labels and messages introduced for preference mapping SHALL be English-only, consistent with current SRS.
