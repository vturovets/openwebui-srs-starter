# CR-005: Synonym Lexicon Generator Utility (OpenAI Responses API)

## Summary

Implement a standalone utility inside `https://github.com/vturovets/openwebui-srs-starter` that generates **up to 10 English synonyms / user utterances** for each **filter option** from an input CSV dataset (e.g., `filters_options_refined_an_131225.csv`) by calling the **OpenAI Responses API** with **Structured Outputs (JSON Schema)**.

The utility will support batching (to handle thousands of rows), enforce domain constraints (English-only, allow abbreviations & typos, avoid codes), and produce a single merged JSON output suitable for downstream semantic mapping / evaluation.

## Background / Business Context

The Semantic Search project maps **free-text preferences** to **existing structured search filter options**. To bootstrap evaluation and improve recall, we need a consistent synonym/phrase lexicon per option (e.g., “all inclusive” → “all incl”, “al inclusive”, etc.).

The lexicon must be reproducible, auditable (inputs/outputs/versioned), and safe for production mapping (high precision, avoid ambiguous noise).

## Goal

Generate a synonym lexicon for each filter option row from the latest dataset (currently: `filters_options_refined_an_131225.csv`) with:

- **English only**

- **include abbreviations and common typos**

- Avoid airport/airline codes (IATA/ICAO + airline codes) for filters DEPARTUREAIRPORTS and CARRIER. Do not remove valid travel abbreviations like AI/HB/BB/RO.

- output in **strict JSON** matching a fixed schema

## Scope

### In scope

1. **CLI utility** to:
   
   - read an input CSV
   
   - validate required columns
   
   - process rows in configurable batches
   
   - call OpenAI Responses API with a fixed prompt + JSON Schema
   
   - write per-batch raw responses (optional) and a final merged JSON file

2. Constraints enforced via prompt + post-validation:
   
   - English-only synonyms
   
   - abbreviations/typos allowed
   
   - Avoid airport/airline codes (IATA/ICAO + airline codes) for filters DEPARTUREAIRPORTS and CARRIER. Do not remove valid travel abbreviations like AI/HB/BB/RO.

3. Resumability:
   
   - ability to resume from an existing output (skip already processed `filterId+optionId`)

4. Logging:
   
   - progress, batch status, errors, retries summary

5. Deterministic-ish behavior controls:
   
   - configurable model name and temperature (default 0.3)

### Out of scope (for this CR)

- Multi-language support

- Automatic taxonomy/ontology creation

- Human review workflow (may be a later CR)

## Assumptions

- The OpenAI API key is provided via environment variable (e.g., `OPENAI_API_KEY`).

- Input CSV includes at least:
  
  - `ID`,`filterId`, `filterName`, `optionId`, `optionName`

- `filters_options_refined_an_131225.csv` is the current baseline dataset; the utility should work with future datasets if columns match.

## Functional Requirements

### FR-1: CLI interface

Provide a CLI command (name can be adjusted to repo conventions), e.g.:

```
python -m tools.synonyms_lexicon \
  --input data/filters_options_refined_an_131225.csv \
  --output out/synonyms_lexicon.json \
  --batch-size 150 \
  --model gpt-5.2 \
  --temperature 0.3 \
  --max-synonyms 10

```

**Required flags**

- `--input <path>`

- `--output <path>`

**Optional flags**

- `--batch-size <int>` (default: 150)

- `--model <string>` (default: `gpt-5.2`)

- `--temperature <float>` (default: 0.3)

- `--max-synonyms <int>` (default: 10; must be between 1 and 10)

- `--resume` (skip rows already present in output)

- `--raw-dir <path>` (store raw API responses per batch for audit)

- `--dry-run` (no API call; only validate & show plan)

- `--rate-limit-sleep <seconds>` (default: small backoff baseline)

- `--max-retries <int>` (default: 5)

- `--timeout <seconds>` (default: 120)

### FR-2: Input validation

On startup, validate that input CSV contains the required columns:

- `ID`, `filterId`, `filterName`, `optionId`, `optionName`

If not, exit with a clear error message.

Also normalize:

- strip BOM from headers if present

- trim whitespace in `optionName`

- ignore extra columns

### FR-3: Batching & ordering

- Process rows in batches of `--batch-size`.

- Maintain stable ordering **within each batch**.

- Output must contain a result for every input row that was processed.

- Final merged output must be in **the same order as the input CSV** including when resuming.

### FR-4: API call (Responses API + Structured Outputs)

For each batch, call `POST /v1/responses` with:

- `instructions`: fixed system-style instructions (“travel-industry semantic search lexicon builder…”)

- `input`: user message containing the batch `ROWS_JSON`

- `text.format`: JSON Schema in strict mode

The schema must enforce output shape:

```json
[
  {
    "ID": "string",
    "filterName": "string",
    "filterId": "string",
    "optionId": "string",
    "optionName": "string",
    "synonyms": ["string"],
    "notes": "string"
  }
]


```

### FR-5: Domain constraints

The utility must enforce the following business rules:

- English only

- include abbreviations & common typos when natural

- Detect suspicious airport/airline code-like tokens (2–4 letters) **only for DEPARTUREAIRPORTS and CARRIER**, and keep a whitelist for AI/HB/BB/RO (and any other approved abbreviations).

Implementation note:

- Primary enforcement via prompt.

- Secondary enforcement via post-processing validation:
  
  - detect suspicious “all-caps 2–4 letter tokens” and remove/flag (without being too aggressive)
  
  - if removals leave 0 synonyms, keep empty list and add notes

### FR-6: Output merge

Write final output JSON file as a **single array** where each entry corresponds to an option row:

- Keys: `ID`, `filterId`, `filterName`, `optionId`, `optionName`, `synonyms`, optional `notes`

- Each array element represents one option row.

### FR-7: Resumability

If `--resume` is set and the output file exists:

- Load existing JSON output.

- Build a processed set by `(filterId, optionId)`.

- Skip those rows.

When resuming, merge results and then reorder final output to match input CSV order.

### FR-8: Audit artifacts

If `--raw-dir` is provided:

- store each raw API response as `raw_dir/batch_<n>.json`

- store the request metadata used for the batch (model, temperature, batch size, timestamp)

## FR-9: Sanitization & Normalization

After the model output, trim whitespace, lowercase (except when casing matters), remove duplicates, enforce `maxSynonyms`, and record removals in `notes`. Notes must record counts + reasons (e.g., `removed=3 (codes=1, duplicates=2)`), without listing removed tokens; raw details go only to `--raw-dir`.



## Non-Functional Requirements

### NFR-1: Reliability

- Retries with exponential backoff on transient failures (429/5xx/timeouts).

- Fail-fast on permanent errors (401/403/invalid schema), with actionable logs.

### NFR-2: Performance

- Default batch size should be safe for ~3–5k rows.

- Processing must provide progress reporting (batch count, rows completed, ETA optional).

### NFR-3: Determinism / Repeatability

- Store run metadata: input file hash, model, temperature, prompt version, date/time, tool version.

- Keep prompt template versioned in repo (file-based).

### NFR-4: Security & privacy

- API key must be read from env var; never written to logs.

- No raw customer personal data is expected in this dataset; nevertheless:
  
  - do not log full payload by default (only counts/ids).
  
  - raw responses optional via `--raw-dir`.

## Prompt Specification (v1)

Store as `prompts/synonyms_lexicon_instructions_v1.txt`.

Core requirements to include (must match BA constraints):

- English only

- allow abbreviations + typos

- avoid airport/airline codes (IATA/ICAO + airline codes) for filters DEPARTUREAIRPORTS and CARRIER. Do not remove valid travel abbreviations like AI/HB/BB/RO

- max 10 synonyms

- short phrases

- high precision over recall

- output in strict JSON schema and maintain ordering as in the input CSV.

## Acceptance Criteria

1. Given an input CSV with required columns, the tool generates an output JSON array.

2. Output JSON validates against the schema:
   
   - each item has `ID`, `filterId`, `filterName`,`optionId`, `optionName`, `synonyms` (0..10 strings)
   
   - optional `notes` allowed

3. The tool does not generate obvious codes (airport/airline codes) in synonyms:
   
   - If model returns them, they are removed/flagged and noted.

4. `--resume` skips previously generated `(filterId, optionId)` pairs and appends new ones.

5. `--dry-run` performs validation and prints intended batch plan without calling the API.

6. `--raw-dir` produces per-batch raw JSON files.

## Risks & Mitigations

- **Risk: cost/latency** for large datasets  
  Mitigation: batching; allow smaller batch size; store raw results; resume.

- **Risk: synonyms too noisy / ambiguous**  
  Mitigation: prompt emphasizes precision; add “notes” field; allow empty synonyms.

- **Risk: false positives in code filtering**  
  Mitigation: keep heuristic conservative; log removals and add notes.
