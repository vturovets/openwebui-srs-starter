# **Solution Design Document**

**Project Title:** NLP-Powered Holiday Request Prototype  
**Version:** 1.0  
**Date:** 2025-11-04

---

# The common baseline (applies to all options)

- **Runtime & API:** Python (e.g., FastAPI) with a single `/parse` endpoint that accepts `{ text, mode, method }`, runs the pipeline, returns the normalized+validated JSON, and appends a CSV row. Voice is optional and included in timing when enabled.

- **Pipeline (fixed order):** detect language → extract → normalize to canonical IDs/codes → validate against fixtures (availability and limits) → enforce required fields (date + from or date + to) → expand dates per flexibility config → build output → log outcome; stopwatch covers the entire run.

- **Validation sources:** `dates.json`, `airports.json`, `destinations.json`, `configuration_search.json` (availability flags, multi-select limits, flexible date ranges, default duration).

- **Interaction mode:** `INTERACTION_MODE=direct-parse` (no questions) or `dialog` (ask clarifying questions when a mandatory parameter is missing/invalid).

- **CSV audit log (append):** `Timestamp, Input, Language, Method, STT, ProcessingTime, Output, Status` (UTF-8).

- **Perf guardrail:** record total processing time and compare to `PROCESSING_THRESHOLD_MS` (default 1000 ms) from `.env`. Voice (if ON) is part of the measurement.

- **Frontend contract:** minimal UI via Open-WebUI (no auth for MVP); backend is a thin HTTP service plug-and-play with that UI.

# Option A — Deterministic “rules-first” parser

**How it works:**  
Use a lightweight rules engine + dictionaries for airports/destinations and a robust date parser. Map “Amsterdam, Ostend” → IATA via your fixtures; map “a week/7 nights” → `durationId`; then run your strict validator exactly as in SRS.

# Option C — Hybrid cascade (recommended)

**How it works:**  
Run Option A first; if anything is **missing/invalid**, ask the LLM **only for the missing bits** (or re-parse the whole text) and then validate again. Always prefer fixture hits from rules; use LLM only to close gaps.

# Suggested API surface (v1)

- **POST `/v1/parse`** → `{ text, mode?, method? }` → `{ language, from[], to[], departureDate[], durationId, party, rooms, status }` and CSV append. The output shape matches your example JSON and mapping table. Enforce success only when (date + from) OR (date + to) are valid after normalization.

- **GET `/v1/fixtures`** → returns the active fixtures (dates/airports/destinations/config) for UI hints and offline tests.

- **POST `/v1/voice`** (optional) → accepts audio if `VOICE_ENABLED=true` and records `STT` in CSV; else a no-op stub to keep perf logic simple.

- **GET `/health`** → quick readiness for Open-WebUI integration.

# Key modules

- **LanguageDetector** (gate to English only in v1).

- **Extractor**: `RulesExtractor` (Option A), `LLMExtractor` (Option B), `HybridExtractor` (Option C).

- **Normalizer**: maps free text → ISO dates, IATA codes, destination IDs, `durationId`.

- **Validator**: enforces availability, counts, flexibility ranges, and the required-fields rule.

- **DialogOrchestrator**: only active when `dialog`.

- **CsvLogger**: appends the exact columns; `ProcessingTime` spans input→render.

- **Config**: reads `.env` (`INTERACTION_MODE`, `ALLOWED_LANGS=en`, `CSV_PATH`, `LLM_METHOD`, `STT_ENGINE`, `VOICE_ENABLED`, `FIXTURES_DIR`, `PROCESSING_THRESHOLD_MS`).
