# Change Request: Phase 1 –Popularity Imputer for OpenWebUI SRS Starter

## Background and current capabilities

The **OpenWebUI SRS Starter** project already includes a
deterministic FastAPI backend that accepts free‑text holiday requests, runs
them through a rule‑based pipeline, normalises the result and validates the
mandatory parameters before emitting a structured search payload. This pipeline
relies on:

- A **rule extractor** that uses dictionaries, synonyms and simple heuristics to locate airports, destinations, durations and dates in the utterance[[1]](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/pipeline/extractor_rules.py#:~:text=class%20RulesExtractor%3A%20,on%20dictionaries%20and%20fixture%20configuration).

- A **normaliser** that converts the extracted signals into canonical values. When the user does not mention a particular field, the normaliser falls back to the configuration defaults: duration defaults to the configured default_duration_id, the party defaults to adults / nonAdults defined in the fixture
  configuration and the number of rooms is set to None if autoRoomAllocationSwitch is enabled[[2]](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/pipeline/normalizer.py#:~:text=def%20_normalize_duration%28self%2C%20extraction%3A%20ExtractionResult%29%20,default_duration_id). These defaults work well for simple queries but are static and do not take historical request popularity into account.

- A **validator** that enforces that at least one departure date is provided, that durations and party sizes are within allowed ranges, and that the number of rooms is valid[[3]](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/pipeline/validator.py#:~:text=def%20_validate_dates%28self%2C%20normalized%3A%20NormalizedResult%29%20,iso_date%7D%27%20is%20not%20available). It also requires that a departure date appears in combination with
  either a departure airport or a destination[[4]](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/pipeline/validator.py#:~:text=def%20_validate_required_combinations%28self%2C%20normalized%3A%20NormalizedResult%29%20,Departure%20date%20is%20required).

Because of these strict requirements, queries such as **“Show me the
cheapest offers”** or **“What are the best cheap hotels in Australia?”** often fail validation: the date, departure airport, party composition and room
count are missing. The existing pipeline does not use any past data to guess
sensible defaults beyond the static values in the configuration. The demo_set_example.csv file
(≈ 47 700 records) contains real user searches with parameters such
as duration, adults, children, infants, startDepartureDate, endDepartureDate, from, rooms and to. This dataset provides a rich source of
information about popular combinations and typical request patterns that can be
exploited to impute missing values for fuzzy queries.

## Phase 1 solution: rule‑based **Popularity Imputer**

### Goals

1.       **Fill missing parameters** when the user provides
an underspecified request. The imputer must infer reasonable values for the
required fields using either global popularity across the entire dataset or
popularity conditional on any parameters the user has supplied.

2.       **Prefer user intent**. If the user mentions a
destination or departure airport in their utterance, those values must be
honoured. Only the missing fields are imputed.

3.       **Use configuration defaults as a fallback**.
Where the dataset does not provide enough information (e.g. extremely rare
destination) or a field is optional, fall back to the existing configuration
defaults (adults/non‑adults, duration and auto‑rooms)[[2]](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/pipeline/normalizer.py#:~:text=def%20_normalize_duration%28self%2C%20extraction%3A%20ExtractionResult%29%20,default_duration_id).

4.       **Modular design**. The imputer should be a
pluggable service that can be swapped out or enhanced in later phases. It
should be independent of the rule extractor and normaliser.

5.       **Fast implementation**. The solution must be
deliverable within five days and operate efficiently on ≈ 47 700
records.

### Algorithm overview

#### **1. Off‑line statistics extraction** (executed at startup or during a build step):

- Load the historic demo_set_example.csv and parse each row into typed values (convert startDepartureDate and endDepartureDate to ISO dates, interpret rooms = 0 as “auto‑allocation”).

- Compute global popularity for each parameter:

| Field                               | Statistic                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| duration                            | Mode (most frequent duration)                                                                                                                                                                                                                                                                                                                                                                                       |
| rooms                               | Mode of non‑zero rooms; if the mode is 0 and autoRoomAllocationSwitch is enabled, treat as None                                                                                                                                                                                                                                                                                                                     |
| party                               | Mode of (adults, children, infants). Only record unique combinations; missing values are treated as zeros                                                                                                                                                                                                                                                                                                           |
| startDepartureDate/endDepartureDate | Mode of the *date interval*. Each row in the historic dataset specifies a startDepartureDate and an endDepartureDate. For popularity we treat this as a closed interval and count how often each unique pair appears. When imputing, select a date **within** the most popular interval (by default choose the interval's start date). If startDepartureDate == endDepartureDate, it indicates a single fixed date. |
| from                                | Mode of departure airport (most common)                                                                                                                                                                                                                                                                                                                                                                             |

- Compute **destination‑specific statistics**: group the dataset by each destination in the to column (split multiple destinations by comma) and compute the same  
  statistics as above for each destination.
- Persist the computed  statistics into a JSON or pickle file under fixtures/ (e.g. fixtures/popularity_stats.json). This avoids re‑computing the counts on every request and isolates  the imputer from the raw CSV.

#### **2. Runtime imputation**:

- Add a new module backend/app/services/popularity_imputer.py that defines a PopularityImputer class. On initialisation it reads the persisted statistics; if the
  file is missing it can recompute from the CSV at startup.

- Expose a method impute(missing:
  dict[str, Any]) -> dict[str, Any] that
  accepts a partially filled parameter dictionary and returns the same
  dictionary with missing fields filled. The method should:

1. Identify which fields (duration, party, rooms, departureDate, from) are missing or empty.

2. Determine the user’s destination(s) (to). If the user specified **exactly one** destination and destination‑specific statistics exist, use those. When **multiple destinations** are specified, attempt to find a departure date that satisfies all
   destinations: intersect the popular date intervals for each destination. If no
   intersection exists, fall back to the configuration default or to the global
   popularity statistics.

3. For each missing field, assign the most popular value from the chosen statistics. When imputing the departure
   date:
- For a single destination, look up the most common (startDepartureDate,
  endDepartureDate) interval and choose a start date **within** that interval (by default use the interval’s start date). When startDepartureDate and endDepartureDate are the same, treat it as a single fixed date.

4. Return the augmented dictionary.

#### **3. Pipeline integration**:

- Introduce a new **imputation step** in the HolidaySearchPipeline inside backend/app/pipeline/pipeline.py. After the extractor returns an ExtractionResult but **before** normalisation and validation, convert the extraction
  into a simple dictionary of candidate parameters. Pass this dictionary to the PopularityImputer.impute method and update the extraction context accordingly.

- For example, if the rule extractor did not detect a departure date, call the imputer to obtain a (startDepartureDate, endDepartureDate) interval and choose a date **within** this interval (typically the start) before updating extraction.dates. Likewise for missing airports, duration and party composition.

- The imputed values should be stored in the extraction context so that
  the normaliser and validator can treat them as if the user had provided them.
  Because the normaliser already converts missing fields to configuration
  defaults[[2]](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/pipeline/normalizer.py#:~:text=def%20_normalize_duration%28self%2C%20extraction%3A%20ExtractionResult%29%20,default_duration_id), the imputer must
  override those defaults when more popular values are available.

- Update the API response metadata to indicate which fields were imputed. This can be
  achieved by adding an imputed field to the PipelineRunResult.metadata dictionary so that the frontend can display “assumed values” back
  to the user.

#### **4. Configuration and extensibility**:

Add new environment variables or configuration keys to control the
imputer:

- POPULARITY_IMPUTER_ENABLED (default true): allows disabling the imputer for debugging; only applied when `LLM_METHOD=hybrid`.

- POPULARITY_DATA_PATH: path to the persisted statistics file (defaults to fixtures/popularity_stats.json).

The PopularityImputer should validate its inputs and log a warning when statistics for a
destination are missing, falling back to global defaults.

All imputer logic must live in its own module under backend/app/services/ so that later phases can replace it with a machine‑learning model without affecting the extraction/normalisation code.

### Example scenarios

**Scenario 1 – completely
unspecified search.** The user types “Show me the
cheapest offers” without mentioning anything else. The rule extractor returns
no airports, destinations or dates. The imputer looks up the global statistics
and fills the missing fields: use the most popular departure date, the most
popular duration, the most common departure airport and the modal party size.
If the configuration enables auto‑room allocation and the mode for rooms
is 0, the imputer returns None for rooms. The pipeline then normalises these values and the validator accepts the request because all mandatory fields are now present.

**Scenario 2 –
destination specified.** The user says “What are the
best cheap hotels in Australia?”. The extractor identifies to = Australia and no other parameters. The imputer reads the statistics for
Australia and fills in the most common departure airport (e.g. “Charleroi”),
departure date (e.g. “2026‑02‑19”), duration (e.g. 7 nights) and party size (e.g. (1 adult, 0
children, 0 infants)). These imputed values
respect the user’s destination while completing the mandatory parameters. 

**Scenario 3 –
multiple destinations without a common date.** Suppose a
user requests “Cheapest offers for Kenya and Japan” and no dates or party size
are mentioned. The imputer first looks up the popular date intervals for Kenya
and Japan separately. It attempts to compute an intersection of those
intervals. If there is no overlap (e.g. the most popular month for Kenya is
March and for Japan is October), then the imputer cannot pick a date that
satisfies both destinations. In this case it falls back to the configured
default departure date or, if none is set, to the most popular global interval.
Other missing fields (duration, party, rooms, departure airport) are filled
using the global or default statistics in the same way.

### Regression coverage and scripted scenarios

- **`test_pipeline_imputes_unspecified_search`** verifies that the validator
  now accepts the “Show me the cheapest offers” utterance by asserting that the
  imputer supplies all mandatory parameters before validation.
- **`test_pipeline_imputes_single_destination_stats`** exercises Scenario 2 with
  “Best cheap hotels in Australia” and confirms that the imputer honours the
  requested destination by sourcing the departure airport and dates from the
  Australia statistics.
- **`test_pipeline_imputes_multi_destination_without_intersection`** mirrors
  Scenario 3 by feeding “Cheapest offers for Kenya and Japan” through the full
  pipeline and asserting that the validator still passes even though the date
  interval falls back to the global popularity window.

These tests live in
`backend/tests/pipeline/test_pipeline_components.py` and run as part of the
standard `pytest` suite.

### Runbook: maintaining the popularity statistics

1. Regenerate the statistics whenever `docs/demo_set_example.csv` changes by
   running:
   ```bash
   poetry run python scripts/build_popularity_stats.py \
       --csv docs/demo_set_example.csv \
       --output fixtures/popularity_stats.json \
       --pretty
   ```
2. Inspect the resulting metadata block in `fixtures/popularity_stats.json` to
   confirm the `schema_version`, source checksum, and generation timestamp.
3. Re-run `pytest backend/tests/pipeline/test_pipeline_components.py` to ensure
   the three regression scenarios still pass with the refreshed data.
4. Capture updated API samples (if behaviour changed) by executing the helper
   snippet in `docs/cr_examples.json` (see the script in this repository that
   generated the file) and commit the refreshed JSON alongside the fixture.

### Limitations and troubleshooting

- Destination intersections require explicit statistics entries. When a user
  supplies multiple destinations that never overlap in the historic dataset,
  the imputer falls back to `source: global` for the departure date, which is a
  signal to log a follow-up data request or prompt the user.
- When the imputer cannot find per-destination statistics it records the names
  in `metadata.imputation.destinationsWithoutStats`; this is useful when
  onboarding new destinations and deciding whether to extend the CSV or the
  fixture dictionaries.
- The departure airport, duration, and party composition always prefer the most
  specific source (`destination:*` → `global` → configuration defaults). If a
  scenario suddenly reports `configuration` for these fields, verify that the
  statistics file still contains the corresponding destination entries.

## Phase 2 preview: **Auto‑completion**

While the popularity imputer fills missing values after the user
submits a query, **phase 2** aims to improve the user experience by
proactively displaying inferred parameters as the user types. A high‑level
design for this phase is as follows:

1.       **Backend suggestions endpoint**. Implement a new FastAPI endpoint /v1/suggestions that accepts the current
text in the input box and returns a JSON payload with suggested values for each
search parameter. The endpoint should reuse the PopularityImputer and destination‑specific
statistics but expose lightweight lookup functions that return the top‑k
popular values rather than a single mode. For example, when the user types
“Austr…”, the endpoint could return the most popular departure dates, durations
and airports for destinations matching the prefix “Austr”.

2.       **Frontend integration**. The Svelte frontend can add an auto‑complete component that debounces
user input and queries the /v1/suggestions endpoint. While the user types, the component displays chips or
dropdown values showing the inferred departure date, duration, party size and
rooms. The user can accept or override these suggestions. Showing the
parameters live emphasises transparency and reduces the risk of surprise
defaults.

3.       **Extensibility**. This endpoint should be implemented in a modular service (e.g. AutoCompletionService) separate from the
popularity imputer so that later phases can be upgraded to ML‑based models
(e.g. gradient‑boosted trees or neural networks) without breaking the API
contract.
