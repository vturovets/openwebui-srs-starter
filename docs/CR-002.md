# Change Request: Phase 2 – Auto‑completion for OpenWebUI SRS Starter

Phase 1 introduced a **Popularity Imputer** to automatically fill missing search parameters using historic popularity statistics. The imputer loads pre‑computed statistics from JSON, intersects date intervals across multiple destinations and falls back to global or configuration defaults when necessary. For example, when the pipeline lacks a departure date the imputer calls its `_select_interval` helper to pick an interval; the selected interval is stored in the imputed metadata and the first date of the interval becomes the search’s `departureDate`[raw.githubusercontent.com](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/services/popularity_imputer.py#:~:text=if%20self,interval%5B0%5D%2C). When multiple destinations are provided, the imputer attempts to find an intersection of their popular intervals. If such an intersection exists it is used; otherwise it falls back to the global interval or the configuration default[raw.githubusercontent.com](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/services/popularity_imputer.py#:~:text=def%20_select_interval%28self%2C%20destinations%3A%20Sequence%5Bstr%5D%29%20,configuration). Similar selection helpers exist for duration, party size, rooms and departure airport[raw.githubusercontent.com](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/services/popularity_imputer.py#:~:text=def%20_needs_duration%28self%2C%20payload%3A%20Mapping,strip).

The imputer returns both the augmented search parameters and metadata describing which values were imputed, enabling the frontend to display assumed values transparently. This mechanism significantly improves the success rate of underspecified queries but still requires the user to press *search* before any defaults are applied. Phase 2 aims to improve the user experience further by providing **auto‑completion suggestions** while the user is typing, thus reducing confusion and allowing the user to confirm or override inferred values proactively.

## Requirements for Phase 2

1. **Realtime suggestions** – As the user types a free‑text holiday request, the interface should display inferred search parameters (e.g. destination, departure date range, duration, party size, number of rooms, departure airport). Suggestions must update live as the user changes the input.

2. **Respect multi‑destination logic** – When the user mentions multiple destinations (e.g. “Kenya and Japan”), the suggestion service must consider the intersection of popular date intervals across those destinations. If no common interval exists, it should fall back to the global popular interval or configuration default[raw.githubusercontent.com](https://raw.githubusercontent.com/vturovets/openwebui-srs-starter/main/backend/app/services/popularity_imputer.py#:~:text=def%20_select_interval%28self%2C%20destinations%3A%20Sequence%5Bstr%5D%29%20,configuration).

3. **Transparency** – Suggested values should be labelled clearly as *suggestions*. If the user chooses to override them, the pipeline must honour the user’s choice (Phase 1’s imputer already takes precedence for explicit user inputs).

4. **Configurable limits** – The number of suggestions returned (e.g. top 3 durations, top 3 airports) and whether auto‑completion is enabled should be configurable via environment variables (`SUGGESTIONS_LIMIT`, `SUGGESTIONS_ENABLED`).

5. **Modularity and extensibility** – The suggestions logic must be implemented as a separate service (e.g. `AutoCompletionService`) so that more sophisticated models (e.g. embeddings or neural networks) can be introduced later without disrupting the existing imputer code.

## Backend changes

1. `AutoCompletionService`

Create a new module `backend/app/services/auto_completion.py` implementing an `AutoCompletionService` class. This service should:

- **Load popularity statistics** (reuse the JSON produced for the Popularity Imputer) and fixture data (destinations, airports, durations) from the existing `FixtureRepository` and `SearchConfiguration`.

- **Resolve partial tokens**. Given a partial input string, attempt to identify partial destinations and airports by matching substrings against the fixture names and synonyms. For example, “Aus” should match “Australia”, “Austrian Alps” etc.

- **Rank suggestions** for each field:
  
  | Field                 | Suggestion Strategy                                                                                                                                                                                                                                                                                                                                          |
  | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | **Destinations**      | Return up to `N` destinations whose names or synonyms contain the partial token, sorted by overall search frequency.                                                                                                                                                                                                                                         |
  | **Departure dates**   | For each candidate destination, retrieve the top `M` popular date intervals. When multiple destinations are present, compute the intersection of their popular intervals; if the intersection is empty, fall back to the global top `M` intervals. Each interval should include both `start` and `end` dates and note when they are equal (single‑day stay). |
  | **Duration**          | Return the top `M` durations (e.g. “7 nights”, “14 nights”) used for the destination(s) or the global top `M` durations when no destination is detected.                                                                                                                                                                                                     |
  | **Party size**        | Suggest common `(adults, children, infants)` combinations from popularity statistics.                                                                                                                                                                                                                                                                        |
  | **Rooms**             | Suggest typical room counts unless `autoRoomAllocationSwitch` is enabled.                                                                                                                                                                                                                                                                                    |
  | **Departure airport** | Suggest the top `M` departure airports for the destination(s) or globally.                                                                                                                                                                                                                                                                                   |

**Return structure** – The service should expose a method `suggest(partial_query: str) -> dict` returning a JSON‑serialisable dictionary with keys `destinations`, `departureDates`, `durations`, `party`, `rooms`, and `from`. Each key maps to an array of suggestion objects with `value` and optional `interval` fields. For example:

{
"destinations": [ { "value": "Australia" }, { "value": "Austria" } ],
  "departureDates": [ { "start": "2026-02-19", "end": "2026-02-19" }, { "start": "2026-03-05", "end": "2026-03-12" } ],
  "durations": [ { "value": "7" }, { "value": "14" } ],
  "party": [ { "value": { "adults": 2, "nonAdults": 0 } } ],
  "rooms": [ { "value": 1 } ],
  "from": [ { "value": "Charleroi" }, { "value": "Liege" } ]
}

2. Suggestions API endpoint
   
   Add a new route to `backend/app/api/routes.py` or similar module:
   
   `@router.get("/v1/suggestions", summary="Return auto‑completion suggestions")
   async def get_suggestions(q: str, limit: int = 3, settings: Settings = Depends(), service: AutoCompletionService = Depends()) -> dict:
       """Return suggested values for each search parameter based on partial input."""
       if not settings.suggestions_enabled:
           return {"suggestions": {}}
       limit = max(1, min(limit, settings.suggestions_limit))
       return {"suggestions": service.suggest(q.strip(), limit)}`

The endpoint uses dependency injection to access the service and settings. `settings.suggestions_enabled` and `settings.suggestions_limit` should be added to the `Settings` class (with appropriate defaults) and documented in `README.md`.

3. Wire up the service
   
   Register an instance of `AutoCompletionService` in the FastAPI dependency graph, similar to how the `PopularityImputer` is registered. The service should be initialised with the same statistics path as the imputer. Optionally, reuse the imputer’s internal statistics to avoid duplication.

4. Unit tests
   
   Add PyTest coverage under `backend/tests/api/test_suggestions.py` to verify that:
   - When `suggestions_enabled` is `False` the endpoint returns empty suggestions.
   
   - For a partial token matching a destination, the endpoint returns the expected sorted suggestions.
   
   - When multiple destinations are provided and no common interval exists, the date suggestions fall back to the global interval.
   
   - The endpoint honours the `limit` parameter.

## Frontend changes

1. API utility

In `frontend/src/lib/api.ts`, implement a function `fetchSuggestions(baseUrl: string, q: string): Promise<SuggestionsResponse>` that calls `/v1/suggestions?q=<user_input>&limit=3`. Reuse `fetch` or the existing wrapper used for `parseText`. 

2. Auto‑complete component

    Add a new Svelte component `AutoComplete.svelte` responsible for displaying suggestions. The component should:

- Accept the current query string as a prop.

- Use a debounced store (e.g. using `setTimeout` or Svelte’s `derived` store) to call `fetchSuggestions` a short time after the user stops typing.

- Render suggestion lists grouped by field. For example, show a list of suggested destinations below the input box and allow the user to click a suggestion to insert it into the query or set the corresponding parameter in the UI.

- Display metadata (e.g. “popular in global data”, “intersection of Kenya||Japan”) returned by the backend so that the user understands why a suggestion is offered.
3. Integrate with the existing input
   
   Modify `App.svelte` to include the `AutoComplete` component below the input field used for `query`. Pass the current query string to the component. When the user selects a suggestion, update the query or call `parseText` immediately with the selected parameters.

4. Styling and UX

Follow the existing design language (Tailwind CSS or custom classes) to style the suggestion lists. Consider adding keyboard navigation (arrow keys and Enter) to improve accessibility. Suggestions should disappear when the input is cleared or the user submits the query.
