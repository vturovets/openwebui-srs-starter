# CR-007: Semantic Preference Mapper

**Repository:** [GitHub - vturovets/openwebui-srs-starter](https://github.com/vturovets/openwebui-srs-starter)  
**Type:** Additive feature (new mapping method)  
**Status:** Proposed  
**Owner:** Semantic Search / BA  
**Priority:** High  
**Target:** Next minor iteration (pilot then refine)

## 1. Background and context

The current preference‑mapping pipeline supports only a simple rule‑based approach (with an LLM/hybrid placeholder). The rule strategy matches surface forms or curated synonyms and is fast, but it cannot handle semantically equivalent phrasing such as **“inexpensive hotel”** vs **“cheap accommodation”**. In free‑text search, users frequently express the same intent using different words or spellings. Articles on semantic matching explain that traditional keyword search fails to find words based on context because it relies on exact term matches[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Traditional%20NLP%20search%20approaches%20have,on%20semantic%20or%20contextual%20meaning). In contrast, modern embedding techniques represent words and sentences as dense vectors where words with similar meanings—even when spelled differently—end up close together[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Word%20embedding%20is%20an%20advanced,close%20to%20similar%20vector%20representations). Cosine similarity between these vectors indicates how related two pieces of text are[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=How%20do%20we%20measure%20if,two%20vectors%20are%20similar). Pre‑trained models like **all‑MiniLM‑L6‑v2** or **all‑mpnet‑base‑v2** can generate high‑quality sentence embeddings[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Thanks%20to%20advancements%20in%20NLP%2C,it%20to%20create%20word%20embeddings) while remaining lightweight enough for low‑latency applications.

CR‑004 describes Mode B (preference mapping) as a key capability: it must interpret a user’s free‑text utterance and map it to one or more filter options defined in `filters_options.csv`. The SRS sets a target accuracy of ≥85 % and a p95 latency of ≤750 ms. To meet these requirements without relying on large generative LLMs, the Semantic Search team evaluated several approaches. **Option 1 – Semantic Embedding and Vector Similarity** from the “Solution Options” document recommends encoding filter options and user queries using a sentence‑embedding model and ranking by cosine similarity. This option promises robust semantic matching and high performance, making it suitable for our MVP.

At present, the repository does not implement a semantic mapping strategy. Implementing Option 1 will close this gap and provide a production‑ready alternative to the rule‑based mapper.

---

## 2. Problem statement

Currently only rule‑based and LLM/hybrid placeholders exist in `backend/app/pipeline/preferences_mapping.py`. The rule mapper uses n‑gram detection and a synonym dictionary to match filter options but cannot recognise paraphrases or synonyms that are not explicitly listed. It also penalises negated matches but offers no semantic understanding. There is no way to choose a “semantic” method via `methods.yaml`, and `configuration.py` rejects any method type outside of `rules`, `llm` or `hybrid`[github.com](https://github.com/vturovets/openwebui-srs-starter/blob/a4e5bcacbf1380e768cb4f43598fc0a6f6aefc6b/backend/app/pipeline/configuration.py#L160-L166). Because of this, Mode B cannot reach the desired 85 % accuracy on diverse user inputs.

## 3. Objectives

### 3.1 Goals

1. **G1 — Semantic mapper implementation.** Add a new `SemanticPreferenceMapper` class that loads a pre‑trained sentence‑embedding model, precomputes embeddings for all filter options, and returns the best matches for a given free‑text query using cosine similarity. Confidence values should reflect similarity scores and support thresholding.

2. **G2 — Method catalogue integration.** Extend the method type enumeration and loading logic to support a new `semantic` method. Provide a default semantic method entry in `config/methods.yaml` with parameters for model name, similarity threshold, and top‑K. Expose these defaults via environment variables.

3. **G3 — Performance targets.** Ensure the semantic mapper meets the p95 latency target of 750 ms without caching, under modest concurrency (≤30 requests/sec). Precompute option embeddings offline at startup and avoid network calls at runtime.

4. **G4 — Negation handling.** Reuse the existing `NegationHandler` to identify and optionally suppress matches that appear in negated phrases (“no breakfast”, “don’t need wifi”).

5. **G5 — Maintain backwards compatibility.** Introducing the semantic method must not change the behaviour of existing rules/LLM/hybrid methods. Existing API signatures remain unchanged.

### 3.2 Non‑goals

- Provide a hybrid combination of semantic and lexical methods (future work).

- Support multi‑language embeddings (English only for v1).

- Persist embeddings in a database; in‑memory caching suffices for now.

## 4. Proposed solution

### 4.1 SemanticPreferenceMapper class

Create a new class `SemanticPreferenceMapper` in `backend/app/pipeline/preferences_mapping.py` (or a new module `semantic.py`) that implements `PreferenceMappingStrategy`. Upon instantiation it will:

1. **Load the model** specified by a new setting `PREF_EMBED_MODEL_NAME` (default: `all-MiniLM-L6-v2`) using the [sentence‑transformers](https://www.sbert.net/) library. Sentence‑transformers models are pre‑trained to produce dense vectors that capture semantic meaning; words with similar meanings have similar vector representations[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Word%20embedding%20is%20an%20advanced,close%20to%20similar%20vector%20representations).

2. **Precompute option embeddings**: Iterate over every filter and option in `FiltersCatalogue`. For each option, build a textual representation (e.g., `f"{filter.label}: {option.label}"`) and encode it into a vector. Store a lookup table mapping `(filter_id, option_id)` to its vector and its norms. This happens once at startup and can be done synchronously during application boot.

3. **Runtime mapping**: When `map(utterance, language=...)` is invoked:
   
   - Use `NegationHandler.apply()` and `TextPreprocessor.preprocess()` to normalise the utterance and obtain any negated spans, mirroring the rule‑based pipeline. The cleaned text is then embedded using the same model.
   
   - Compute cosine similarity between the query vector and each precomputed option vector. Cosine similarity is used because it measures orientation and is scale‑invariant[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=How%20do%20we%20measure%20if,two%20vectors%20are%20similar). Optionally pre‑normalise vectors to reduce per‑call cost. For each option, record its similarity score.
   
   - Sort results by similarity and select options above a configured threshold `similarity_threshold` or the top‑`K` results specified in the method parameters. Each candidate becomes a `FilterOptionSelection` with `confidence = similarity` and `selected = (similarity ≥ similarity_threshold and not negated)`. If the option text appears in a negated span, mark `selected=False` but still return the match for UI transparency.
   
   - Group selected options into `FilterSelection` objects per filter and build the `mappings` payload analogous to the rule mapper (include matched phrases and confidence scores). If no options exceed the threshold, return status `no-preferences-detected`.

An auxiliary caching layer may be added later to store user query embeddings for repeated queries, but is not required in v1.

### 4.2 Configuration changes

1. **Extend supported method types.** Update `_build_method_config` in `backend/app/pipeline/configuration.py` to accept `semantic` as a valid method type alongside `rules`, `llm` and `hybrid`. This avoids raising an exception when `methods.yaml` declares a semantic method[github.com](https://github.com/vturovets/openwebui-srs-starter/blob/a4e5bcacbf1380e768cb4f43598fc0a6f6aefc6b/backend/app/pipeline/configuration.py#L160-L166).

2. **Add `semantic` strategy to PreferencesPipeline.** Modify `PreferencesPipeline._build_strategies()` to instantiate a `SemanticPreferenceMapper` when the method kind is `semantic`. Provide it with the filter catalogue, synonym store (for negation handling), similarity threshold, and model parameters from the method’s config.

3. **Update methods catalogue.** In `config/methods.yaml`, add a new entry:

```yaml
methods:
  - id: semantic-basic
    type: semantic
    label: "Semantic mapping (MiniLM)"
    description: "Use sentence embeddings and cosine similarity to match user preferences to filter options"
    params:
      similarity_threshold: 0.35
      top_k: 5
      model_name: ${PREF_EMBED_MODEL_NAME:-all-MiniLM-L6-v2}
    enabled: true
```

Set `default` to `semantic-basic` in pilot environments, and allow overriding via the `LLM_METHOD` environment variable. Expose the parameters `similarity_threshold`, `top_k` and `model_name` through `Settings` so that deployments can tune sensitivity without code changes.  

4. **Add environment variables.** Introduce new settings in `backend/app/config.py`:

```python
pref_embed_model_name: str = Field(default="all-MiniLM-L6-v2", alias="PREF_EMBED_MODEL_NAME", description="Name of the sentence-transformer model used for semantic preference mapping.")
pref_embed_similarity_threshold: float = Field(default=0.35, alias="PREF_EMBED_SIMILARITY_THRESHOLD", description="Minimum cosine similarity required to mark an option as selected.")
pref_embed_top_k: int = Field(default=5, alias="PREF_EMBED_TOP_K", description="Number of top options to consider if no thresholded options are found.")

```

Update `PreferencesPipeline._build_strategies()` to pass these values into the semantic mapper’s constructor.

### 4.3 Dependency management

Add `sentence-transformers>=2.2.0` to the Python dependencies (e.g., `requirements.txt`). This library includes the `SentenceTransformer` class and cosine similarity utilities. Because the models are small (~90 MB for MiniLM) they can be loaded on CPUs within tens of milliseconds, and the entire query + similarity computation easily fits within the p95 750 ms budget[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Thanks%20to%20advancements%20in%20NLP%2C,it%20to%20create%20word%20embeddings). No external network requests are needed, ensuring deterministic latency and no usage of prohibited LLM services.

### 4.4 Negation handling

Reuse the existing `NegationHandler` and `TextPreprocessor` to detect negated phrases in the user utterance. If an option’s label (or one of its synonyms) appears within a negated span, mark that option as not selected (`selected=False`) and reduce its confidence by a configurable penalty (reuse the existing `preferences_rules_negation_penalty`). This approach mirrors the rule‑based mapper and maintains interpretability.

## 5. Design decisions

1. **Model choice (MiniLM vs mpnet).** MiniLM and MPNet are both sentence‑transformer models that produce high‑quality sentence embeddings. We propose defaulting to `all-MiniLM-L6-v2` because it is smaller and faster, yet still captures semantic relationships and synonyms[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Thanks%20to%20advancements%20in%20NLP%2C,it%20to%20create%20word%20embeddings). Projects may override to `all-mpnet-base-v2` if they prioritise accuracy over latency.

2. **Text representation.** We embed `"{filter label}: {option label}"` to give context and reduce ambiguity between similarly named options. In future iterations we may incorporate synonyms into the centroid (as described in CR‑006) but will start simple.

3. **Cosine similarity as confidence.** Cosine similarity ranges from 0 to 1; a higher value indicates that the user query and option are more semantically aligned[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=How%20do%20we%20measure%20if,two%20vectors%20are%20similar). We expose the similarity threshold to tune the trade‑off between precision and recall.

4. **Negation penalty reuse.** To remain consistent with the existing rule‑based logic, we reuse the `preferences_rules_negation_penalty` when a negated match is detected. This avoids adding new penalty parameters.

5. **Optional ANN search.** Given the small number of filter options (~3 500), brute‑force dot‑product search is sufficiently fast. Should the option catalogue grow significantly, the semantic mapper can be extended to use an approximate nearest‑neighbour library (e.g., FAISS or Annoy) without affecting its interface.

## 6. Interfaces and configuration

### 6.1 Method catalogue

The existing `MethodsCatalog` will accept a new method of type `semantic`. Users can select it via the `method` query parameter on the `POST /preferences` endpoint or by setting the `LLM_METHOD` environment variable to `semantic-basic`.

### 6.2 Configuration parameters

| Setting                              | Default            | Description                                                         |
| ------------------------------------ | ------------------ | ------------------------------------------------------------------- |
| `PREF_EMBED_MODEL_NAME`              | `all-MiniLM-L6-v2` | Name of the sentence transformer model used for embeddings.         |
| `PREF_EMBED_SIMILARITY_THRESHOLD`    | `0.35`             | Minimum cosine similarity required to mark an option as selected.   |
| `PREF_EMBED_TOP_K`                   | `5`                | Number of top options to return if no option exceeds the threshold. |
| `PREFERENCES_RULES_NEGATION_PENALTY` | `0.25` (unchanged) | Penalty applied to confidence when a match is negated.              |

These parameters can be overridden per environment via `.env` or process variables. They are also surfaced in `config/methods.yaml` under the `params` section for the semantic method.

## 7. Data contracts

This CR does **not** introduce new API endpoints or response formats. The `PreferencesPipeline.run()` method will return the same `PreferenceRunResult` structure: `status`, `method_requested`, `method_used`, `detection`, `filters`, `timings`, `metadata`, `mappings`, `error`. The difference is that when `method_used` is `semantic-basic`, the `filters` list will be produced by `SemanticPreferenceMapper`. Confidence values in each filter option payload reflect cosine similarity scores; they remain floats between 0 and 1.

## 8. Functional requirements

### FR‑1 Semantic model loading

- The semantic mapper must load the sentence‑embedding model specified by `PREF_EMBED_MODEL_NAME`. If the model cannot be loaded (file missing or incompatible), an exception must be raised during application start‑up, causing the semantic method to be unavailable.

### FR‑2 Option embeddings precomputation

- When the semantic mapper is first created, it must iterate through all `FilterDefinition` objects and compute an embedding for each option. Results are cached in memory for subsequent queries. Precomputation must complete within 2 seconds on a typical developer machine.

### FR‑3 Utterance embedding and similarity calculation

- For each call to `map()`, the mapper must embed the cleaned utterance, compute cosine similarity against each option vector, and produce confidence scores. The implementation must avoid repeated re‑normalisation of vectors for efficiency.

### FR‑4 Thresholding and selection

- Options whose similarity score is equal to or above `similarity_threshold` (default 0.35) are marked `selected=True`, unless negated. If no options exceed the threshold, the mapper must still return the top `K` results (`PREF_EMBED_TOP_K`) with `selected=False` to allow UI display of potential matches.

### FR‑5 Negation handling

- The semantic mapper must use `NegationHandler` to identify negated spans in the utterance. If an option’s label (or its synonyms) occurs within a negated span, reduce its confidence by `preferences_rules_negation_penalty` and set `selected=False`.

### FR‑6 Method catalogue integration

- The `MethodsCatalog` must accept the `semantic-basic` method and return it when looked up by id or type. If no `semantic` method is enabled, the system must fall back to the default method.

### FR‑7 Error handling

- Failures in embedding (e.g., invalid model path) should result in `status="invalid-catalogue"` with an explanatory error in the `PreferenceRunResult`. These errors should not crash the application.

## 9. Non‑functional requirements

### NFR‑1 Performance

- The semantic mapper must process a single query in ≤750 ms at the 95th percentile under nominal load. With precomputed embeddings, embedding the utterance and computing ~3.5k dot products should complete in <300 ms. Loading the model must happen only once.

### NFR‑2 Resource usage

- The additional memory footprint for storing 3 500 option vectors (~768 dimensions each) must not exceed 50 MB. The sentence transformer model (~90 MB for MiniLM) must be loaded into memory once and shared across requests.

### NFR‑3 Observability

- Extend existing logging to record the time spent in the semantic mapping phase and the number of options returned. Do not log embedding vectors or sensitive data. Record threshold breaches in the import summary if semantic mapping exceeds `PROCESSING_THRESHOLD_MS`.

### NFR‑4 Security

- Do not transmit user utterances to external services during semantic mapping. All inference must occur locally using the loaded model. Only environment variables and configuration files may influence behaviour.

### NFR‑5 Backwards compatibility

- All existing unit and integration tests must continue to pass. New tests must be added for the semantic mapper. No changes are allowed to the public API or payload structure.

## 10. Test approach

### 10.1 Unit tests

1. **Model loading test:** Verify that `SemanticPreferenceMapper` raises a clear exception when an invalid model name is provided and successfully loads when a valid model is provided.

2. **Embedding precomputation test:** Ensure that embeddings are generated for every option in the catalogue and cached. Validate the shape and dtype of the generated matrix.

3. **Similarity computation test:** Create synthetic options with known text and verify that queries like “cheap stay” rank the “inexpensive” option higher than unrelated options, demonstrating that semantically similar words produce similar vectors[freecodecamp.org](https://www.freecodecamp.org/news/what-is-semantic-matching-find-words-in-a-document-using-nlp/#:~:text=Word%20embedding%20is%20an%20advanced,close%20to%20similar%20vector%20representations).

4. **Threshold behaviour test:** Verify that options above the threshold are marked `selected=True` and those below are not. Check the fallback to top‑`K` results when none pass the threshold.

5. **Negation test:** Provide utterances with negated preferences (“no pool”) and verify that the associated option is returned with `selected=False` and reduced confidence.

6. **Method catalogue test:** Ensure that the semantic method appears in the loaded catalogue and can be selected via `LLM_METHOD=semantic-basic`.

### 10.2 Integration tests

1. **End‑to‑end mapping:** Using the default catalogue, send sample utterances through `PreferencesPipeline.run()` with method `semantic-basic`. Verify that expected options (e.g., “diving facilities” → “Scuba Diving”) are selected and that performance metrics (`mappingMs`) remain under 500 ms for typical utterances.

2. **Fallback behaviour:** If the semantic method is disabled or misconfigured, verify that the pipeline falls back to the default method and returns rule‑based results.

3. **Configuration overrides:** Test different combinations of `PREF_EMBED_MODEL_NAME`, `PREF_EMBED_SIMILARITY_THRESHOLD`, and `PREF_EMBED_TOP_K` via environment variables and confirm they change behaviour accordingly.

### 10.3 Manual smoke test

- Deploy the pipeline with the semantic method enabled and use the UI to enter diverse free‑text preferences (e.g., “no meals, but close to the beach with free wifi”). Confirm that the semantic mapper returns relevant filters (e.g., “Room Only”, “Beachfront”, “Free Wi‑Fi”) and excludes negated options (“All Inclusive”).

- Measure response times via logs or the import summary and ensure latency remains within budget.

## 11. Acceptance criteria

1. The new `SemanticPreferenceMapper` class exists and implements the logic outlined in this CR. It loads the model, precomputes option embeddings, embeds queries, computes cosine similarity, handles negations, and produces `FilterSelection` objects.

2. `configuration.py` recognises `semantic` as a valid method type, and `methods.yaml` includes a `semantic-basic` entry that can be selected via environment variables or API.

3. `Settings` exposes `PREF_EMBED_MODEL_NAME`, `PREF_EMBED_SIMILARITY_THRESHOLD`, and `PREF_EMBED_TOP_K` and passes them into the mapper.

4. Unit and integration tests covering semantic mapping and configuration are implemented and pass. No existing tests fail.

5. The semantic mapper meets the accuracy and performance targets: end‑to‑end mapping under 750 ms at p95 and accuracy approaching or exceeding 85 % on internal evaluation datasets (e.g., utterances generated by CR‑006’s utility).

6. The API surface (request and response schemas) remains backward compatible; clients can continue to consume `PreferenceRunResult` without changes.



## 12. Risks and mitigations

| Risk                                                                                                                                             | Mitigation                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Model size/initialisation overhead** — loading the embedding model could delay startup or exhaust memory.                                      | Choose a lightweight default model (MiniLM). Document the one‑time cost and allow asynchronous warm‑up.                  |
| **Low separability between some options** — semantically similar options (e.g., “Spa” and “Wellness centre”) may produce high similarity scores. | Consider adjusting the context string for embeddings or including synonyms. Provide a configurable similarity threshold. |
| **Threshold tuning** — a fixed threshold may be too strict or too lenient across all filters.                                                    | Expose `PREF_EMBED_SIMILARITY_THRESHOLD` in the config. Use CR‑006’s utterance generator to tune thresholds empirically. |
| **Negation edge cases** — the semantic mapper might select options if the negation detection fails (e.g., double negatives).                     | Reuse `NegationHandler` logic and test with typical negation patterns.                                                   |
| **External library maintenance** — `sentence-transformers` may introduce breaking changes.                                                       | Pin the dependency version in `requirements.txt` and monitor release notes.                                              |
