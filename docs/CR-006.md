# CR-006: Utterance Dataset Generator Utility (Single-Option + Multi-Option)


**Repository:** https://github.com/vturovets/openwebui-srs-starter  
**Type:** Additive feature (new utility)  
**Status:** Ready for implementation  
**Owner:** Semantic Search / BA  
**Priority:** Medium  
**Target:** Next minor iteration (pilot first, then tune thresholds)

---

## 1. Background and context

The Semantic Search project aims to improve user experience by mapping **free-text preferences** to existing **structured filter options**.  
A lexicon exists that enumerates filter options and their synonyms (per option):  
`{ ID, filterId, filterName, optionId, optionName, synonyms[] }`.

To evaluate mapping methods (accuracy + performance), we need a **labeled dataset** of:

- **Single-option utterances** (clean labels, one option only)
- **Multi-option mini-queries** (2–4 options across filters)

This CR introduces a separate **utility** within the repo to generate and score such datasets.

---

## 2. Problem statement

Currently, the repo does not provide a built-in tool to:

1) Generate realistic utterances from the lexicon,  
2) Enforce **single-option purity** (avoid implying other filters),  
3) Generate **multi-option combinations** (2–4 options across filters),  
4) Quantify dataset quality/ambiguity via a consistent **semantic closeness** score.

As a result, benchmarking mapping approaches is slower, less repeatable, and less robust.

---

## 3. Objectives

### 3.1 Goals

**G1 — Single-option dataset generation**

- Generate **up to 3 utterances per option**
- Include both:
  - `preference_only` (short fragments)
  - `mini_query` (short query phrasing)
- Provide `easy | medium | hard` variations **only via wording/paraphrase**
- Enforce **purity constraint**: each utterance must imply **only** the target option.

**G2 — Multi-option dataset generation**

- Generate mini-queries implying **2–4 options** across different filters
- Combinations produced deterministically (seeded), with configurable size distribution

**G3 — Semantic closeness scoring**

- Compute embeddings-based semantic closeness for:
  - single-option purity gating
  - multi-option coverage/separation diagnostics

**G4 — Repeatability & usability**

- CLI-first; PowerShell-friendly
- Batch processing with retries/backoff
- Outputs as JSONL/JSON/CSV + run manifest

### 3.2 Non-goals

- No changes to existing API endpoints or UI behavior
- No contradiction ruleset (e.g., “adults-only vs family-friendly”) in v1
- No labeling UI; only file-based outputs

---

## 4. Proposed solution

Add a new utility module (recommend one of):

- `scripts/utterance_generator/` (preferred for “tooling”)
- `backend/app/tools/utterance_generator/` (if you prefer backend-owned utilities)

The utility provides three modes:

1) **single** — generate 1–3 utterances per option (strict purity)
2) **multi** — generate multi-option combinations + one mini-query per combination
3) **score** — compute embedding-based metrics and produce a scoring report

The generator uses the OpenAI Responses API with **Structured Outputs** (JSON Schema) to ensure parseable results.

---

## 5. Design decisions (final)

### 5.1 Contradiction ruleset

**Decision:** No explicit contradiction ruleset in v1.  
**Reason:** Keep v1 minimal; rely on embedding-based separability metrics and mapping evaluation results to surface issues.

### 5.2 Centroid composition

**Decision:** Option centroid uses **synonyms + optionName** with equal weights.

### 5.3 Similarity metric (explicit)

**Decision:** Semantic closeness is computed using **cosine similarity** between:

- utterance embedding `u`
- option centroid embedding `c_o`

## 6. Interfaces and configuration

### 6.1 CLI commands (proposed)

**A) Single-option generation**

```bash
python -m utterance_generator single \
  --lexicon fixtures/synonyms_lexicon.json \
  --out data/utterances_single.jsonl \
  --max-per-option 3 \
  --purity-mode strict \
  --batch-size 75
```

**B) Multi-option generation**

```bash
python -m utterance_generator multi \
  --lexicon fixtures/synonyms_lexicon.json \
  --output data/utterances_multi.jsonl \
  --count 50 \
  --allow-same-filter \
  --single-option-filter-id MEAL_PLAN \
  --single-option-filter-id ACCESSIBILITY
```

**C) Scoring / validation**

```bash
python -m utterance_generator score \
  --lexicon fixtures/synonyms_lexicon.json \
  --dataset data/utterances_single.jsonl \
  --out data/score_report.json \
  --embedding-model text-embedding-3-small \
  --purity-margin 0.10 \
  --purity-min-score 0.38 \
  --topk 10
```

### 6.2 Environment variables (recommended)

- `OPENAI_API_KEY` (required)

- `UTT_GEN_MODEL` (default: repo default LLM model)

- `UTT_EMBED_MODEL` (default: `text-embedding-3-small`)

- `UTT_TIMEOUT_S` (default: 60)

- `UTT_MAX_RETRIES` (default: 6)

Includes:

- aggregate: acceptance rate, ambiguity rate, per-filter stats

## 8. Scoring definitions (centroid + cosine)

### 8.1 Option centroid

For each option `o`:

- Embed `optionName`

- Embed every `s in synonyms[]`

- Compute centroid as mean (equal weights)

co​=mean({embed(optionName)}∪{embed(s)∣s∈synonyms})

### 8.2 Utterance embedding

u=embed(utterance)

### 8.3 Similarity metric (cosine)

score(o,u)=cosine(u,co​)=∥u∥∥co​∥u⋅co​​

> Note: If vectors are already normalized by the embedding model/provider, cosine is equivalent to dot product; however, cosine remains the canonical metric for clarity and portability.

### 8.4 Derived metrics

- `top1`, `top2`: highest and second-highest cosine score options

- `margin = score(top1) - score(top2)`

**Multi-option diagnostics** for intended matched set `M`:

- `coverage = min_{o in M} score(o,u)`

- `strength = mean_{o in M} score(o,u)`

- `separation = min_{o in M} score(o,u) - max_{o notin M} score(o,u)`

## 9. Functional requirements

### FR-1 Lexicon loader

- Load lexicon JSON and validate required keys and types

- Fail fast with actionable error messages

### FR-2 Single-option utterance generation (strict purity)

For each option:

- Generate **1–3 utterances**

- Prefer including both types when `max-per-option >= 2`:
  
  - at least 1 `preference_only`
  
  - at least 1 `mini_query`

- Tag each utterance with `difficulty`

**Purity constraint (critical):**

- Each utterance must **not strongly imply any other filter option**

- No bundling of unrelated preferences

- No airport/airline codes (IATA/ICAO); no internal IDs

- “Hard” means wording is less direct; **not** adding extra preferences

### FR-3 Multi-option combination generator

- Generate combinations of **2–4 options**

- Default: **no duplicate `filterId`** inside one combination (configurable)

- Allow cross-filter combinations (required)

- No contradiction filtering in v1

### FR-4 Multi-option mini-query generation

- For each combination, generate **exactly one** mini-query implying all options

- No internal IDs; no IATA/ICAO codes

### FR-5 Structured outputs enforcement

- All LLM outputs must be schema-conformant (JSON Schema strict mode)

- Utility must reject/redo responses that do not parse or do not match schema

### FR-6 Scoring

- Build centroids from **synonyms + optionName**

- Compute cosine similarity scores for all options against each utterance

- Produce top-k ranking + derived metrics

### FR-7 Purity gate (single-option acceptance)

Apply the default acceptance criteria (configurable):

- top-1 must equal the target option

- margin must meet threshold

- (optional) minimum score must meet threshold

Rejected utterances must be saved with reasons.

### FR-8 Outputs and reproducibility

- Write datasets as JSONL (preferred), optionally JSON/CSV

- Write a `run_manifest.json` capturing:
  
  - model names, temperatures, batch sizes, thresholds, timestamps, seed, lexicon hash

## 10. Non-functional requirements

### NFR-1 Performance and batching

- Batching defaults:
  
  - generation: `75 options/call` (configurable)
  
  - embeddings: `200 texts/call` (configurable)

- Retry on transient errors (429/5xx) with exponential backoff + jitter

### NFR-2 Observability

- Log:
  
  - counts (generated/accepted/rejected)
  
  - retry stats
  
  - latency per batch
  
  - acceptance and ambiguity rates

- Do not log API keys or sensitive environment values

### NFR-3 Security

- Read secrets only from env/.env

- Never persist keys into outputs or logs

### NFR-4 Backward compatibility

- Utility is additive and optional; no changes to existing runtime features

## 11. Default parameters (best guess for pilot)

All defaults must be CLI-configurable.

### 11.1 Single-option purity defaults (STRICT)

Accept iff:

1. `top1 == target option`, AND

2. `margin >= 0.10`, AND

3. `score(top1) >= 0.38` (enabled by default)

Defaults:

- `--purity-margin 0.10`

- `--purity-min-score 0.38`

- `--topk 10`

### 11.2 Multi-option diagnostics defaults (no hard rejection)

Compute and report; do not reject by default.

Soft flags (reported only):

- `flag_low_coverage` if `coverage < 0.30`

- `flag_low_separation` if `separation < 0.05`

Defaults:

- `--multi-coverage-flag 0.30`

- `--multi-separation-flag 0.05`

### 11.3 Generation defaults

- `--max-per-option 3`

- Difficulty assignment (best effort):
  
  - 3 utterances: easy + medium + hard
  
  - 2 utterances: easy + hard
  
  - 1 utterance: medium

## 13. Acceptance criteria

1. Utility runs via CLI on Windows (PowerShell).

2. Single-option mode generates ≤3 utterances per option and enforces strict purity.

3. Purity gate produces accepted + rejected outputs with reasons.

4. Multi-option mode generates N combos (2–4 options across filters) and one mini-query each.

5. Scoring mode produces a report with cosine scores, top-k matches, and ambiguity metrics.

6. No existing repo tests break; utility is additive only.

## 14. Risks and mitigations

- **Risk:** Thresholds too strict/lenient → acceptance rate too low/high  
  **Mitigation:** pilot run, then tune margin/min-score based on distributions.

- **Risk:** Some options are semantically close (overlapping synonyms) → low separability  
  **Mitigation:** scoring report highlights hotspots; consider lexicon refinement or option grouping later.

- **Risk:** LLM occasionally outputs bundled preferences in single-option mode  
  **Mitigation:** strict purity instructions + purity gate + regeneration loop.

## 15. Open items (post-pilot tuning)

- Tune `purity-margin` and `purity-min-score` after pilot run:
  
  - target acceptance rate (e.g., 70–90% for single-option)
  
  - review top confusion pairs and adjust prompts/lexicon if needed

- Consider optional weighting of optionName vs synonyms (future enhancement; not required for v1)
